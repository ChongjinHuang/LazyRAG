# Diagram Design

Create a clear diagram as self-contained HTML with inline SVG and CSS. Preserve the user's facts; ask once for missing information that changes essential nodes, order or branches. Mark reasonable assumptions beside the diagram. Do not read the whole package.

## Resolve style and select a type

1. Before every diagram, inspect the project root for `.diagram-design`. Resolve the effective style using the generation rules in `references/core-rules.md`, then read that guide. `references/profiles.md` is for explicit profile management or a resolution/recovery question the core rules do not answer; do not load its full save/load/list/update/delete procedures for ordinary generation. Read `references/onboarding.md` only for brand customization.
2. Read `references/core-rules.md` and the selected type reference; request independent references together where supported. Reuse their contents during this diagram rather than fetching them again. Common routes: decision/approval paths → `references/type-flowchart.md`; time-ordered messages → `references/type-sequence.md`; components/connections → `references/type-architecture.md`; role handoffs → `references/type-swimlane.md`. For other or ambiguous needs, read `references/type-index.md`, which retains all 39 type routes and use boundaries. If behavior, state, enforcement or risk carries the meaning, select a semantic pattern using `references/semantic-patterns.md` before choosing layout. Read `references/type-budgets.md` only for a type with a specialized budget or when near its limit.
3. Briefly state the type/pattern, size and planned cuts; allow redirection when these are uncertain. Proceed directly when already specified, or note assumptions if the user is unavailable. Read `references/presentation.md` when adding summary cards, selecting a non-default variant, or needing template details; the default light diagram does not require that reference; read animation/icon/annotation references only when those features are needed. Read the selected guide’s series palette, terminal skin or CJK sections only when those features are needed. The original default is minimal light (diagram and title), static, using `assets/template.html` when a starting file is useful; summary cards and other variants remain optional. Examples are optional; do not load them just to confirm the default.

## Draw, validate and deliver

- The mandatory core rules already contain the connector and SVG contracts. Read `references/svg-primitives.md` only if an implementation detail or code example is still needed; `references/design-details.md` preserves the complete upstream design/output checks for questions the compact rules do not answer.
- For existing draw.io or Mermaid sources, read `references/import-guide.md` then the matching import reference. `scripts/mermaid_extract.py <existing-file>` and `scripts/drawio_extract.py <existing-file>` parse sources for redrawing; they are not generators and do not accept node/title/output-format arguments. For prose requirements, author the HTML directly. Export PNG/SVG only when requested, per `references/export.md`.
- Save the complete HTML using the available writing tools, then run the original `scripts/self_check.py <absolute-html-path>` (through `run_skill_script` when available). Repair failures and rerun the check before the final reply. Apply the original type/core checklist too; self-check does not prove all geometry/taste rules.
- In LazyMind, use `save_chat_artifact` to make the HTML available in the conversation. Follow its supported input modes: inline HTML can be saved as `text`, or an existing file as `file`. The save tool may also be the available writer that creates the file for self-check; it is not a separate mandatory filesystem workflow. If checking requires corrections, update the saved artifact and check the corrected file. Never claim a check passed unless it ran successfully. A workspace file alone is not delivery: include the returned `file_markdown` in the final reply. Once the diagram and checks are complete, give the link and a concise summary; further refinements require a user request.
